# Development Guide

## Prerequisites

- Docker + Docker Compose plugin
- (Optional, for non-Docker local dev) Python 3.11+, Node 20+

## Project layout

```
backend/    FastAPI app, Alembic migrations, pytest suite, seed script
frontend/   React + TypeScript + Vite app
docker-compose.yml
```

## Day-to-day backend workflow (Docker-based, no local Python install needed)

Rebuild after changing backend code or `requirements.txt`:

```bash
docker compose build backend
docker compose up -d backend
docker compose logs -f backend
```

Run a one-off command in a throwaway container (useful for migrations/scripts without restarting the running service):

```bash
docker run --rm --network atsai_default -v "$(pwd)/backend:/app" -w /app \
  -e DATABASE_URL="postgresql+psycopg2://ats:ats@ats-postgres:5432/ats" \
  atsai-backend:latest <command>
```

(Replace `atsai_default` with whatever `docker network ls` shows for this project if it differs — Compose derives it from the project directory name.)

### Migrations

```bash
docker compose exec backend alembic revision --autogenerate -m "add X column"
docker compose exec backend alembic upgrade head
```

Review every autogenerated migration before committing — Alembic doesn't always get enum/index changes exactly right, and the `embeddings` table's `CREATE EXTENSION IF NOT EXISTS vector` needs to stay at the top of the very first migration's `upgrade()`.

### Seeding

```bash
docker compose exec backend python -m app.seed
```

Safe to re-run (skips existing users/labels/jobs; adds another batch of candidates each time — truncate the relevant tables first if you want a clean slate, see the one-liner in `README.md`'s testing section or just `docker compose down -v` to start from scratch).

### Tests

```bash
docker compose exec -e DATABASE_URL=postgresql+psycopg2://ats:ats@postgres:5432/ats_test backend pytest -q
```

The test suite auto-creates/truncates a separate `ats_test` database — your dev data is never touched. `tests/factories.py` builds in-memory `.docx` files (via `python-docx`) so upload/parsing tests exercise the real pipeline end-to-end rather than mocking it.

When writing a new test that generates a sample CV, make sure every persona-specific string (skills, summary, experience description) actually varies with the test's inputs — a hardcoded phrase like "using FastAPI and Qdrant" baked into every generated CV will silently make unrelated candidates match on those keywords in search/screening tests (we hit exactly this bug once; see git history / `tests/factories.py`).

## Day-to-day frontend workflow

```bash
cd frontend
npm install
npm run dev            # http://localhost:5173, expects the backend at VITE_API_URL (see .env.example)
npm run build           # type-check + production build
```

## Adding a new backend feature

Follow the existing layering — don't put logic in routers:

1. Model (`app/models/`) + Alembic migration.
2. Schema (`app/schemas/`) — request/response Pydantic models.
3. Service (`app/services/<area>/`) — the actual logic, takes a `Session` and plain arguments, returns ORM objects or plain data.
4. Router (`app/api/v1/<area>.py`) — thin: validate input via the schema, call the service, map to a response schema.
5. Tests in `backend/tests/`.

If the feature touches AI (a new kind of LLM call or embedding use), add a prompt builder function in `app/prompts/` — never inline a prompt string in a service or route.

### Adding another AI provider

To add a provider beyond OpenAI/Gemini: implement `LLMService`/`EmbeddingService` (see `app/services/llm/gemini_service.py` for the shortest reference implementation), then add its key(s) to `Settings` (`app/core/config.py`, following the `*_API_KEY` / `*_API_KEYS` pattern) and wire it into `build_pool()` (`app/services/ai_common/key_pool.py`) and the two factories (`llm/factory.py`, `embedding/factory.py`). You get key rotation/failover for free — `RotatingLLMService`/`RotatingEmbeddingService` don't know or care which providers are in the pool. Remember: embeddings from different providers have different dimensions, so a provider only belongs in the *embedding* pool if it matches `EMBEDDING_DIM`, or you've migrated the `embeddings.vector` column to match.

Rebuild the backend image after changing `requirements.txt` or the `Dockerfile` (e.g. after adding OCR's `tesseract-ocr`/`poppler-utils` system packages) — `docker compose build backend`.

## Code style / conventions

- No business logic in FastAPI route functions.
- Every LLM-facing prompt lives in `app/prompts/`, built by a small pure function that returns `(system_prompt, user_prompt)`.
- Every provider-specific integration (OpenAI, etc.) sits behind an abstract base class with a `Mock*` default that has real logic (not a stub) so the product works without any API key.
- Candidate history is written via `candidate_service.log_activity(...)` for every meaningful mutation (upload, screening, stage change, assessment, label change, merge) — never skip this when adding a new mutation on a candidate.
- Merges never delete data — always re-point and log, never `DELETE`, on the source candidate's related rows.
